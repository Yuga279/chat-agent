# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- `server/` — the chat agent backend (Express + LangGraph + MongoDB). This is where almost all work happens.
- `web/` — a React + TypeScript + Vite frontend (login/signup, a single chat view). Built with `npm run build` into `web/dist/`, which `server/`'s Express app serves as static files in production; `npm run dev` runs a hot-reload Vite server on `:5173` that proxies `/auth` and `/api` to `:3200` during development.
- `System1.MCP/` — a **separate, sibling** project: an MCP server (Express + `@modelcontextprotocol/sdk`, backed by `better-sqlite3`) that exposes System1 ClockWork time-tracking tools (start/stop/delete entry, list projects/tasks). `server/` is purely an MCP *client* of it, talking over HTTP; the URL is configured via `MCP_SERVER_URL`. Treat it as out-of-repo unless a task explicitly touches it — it has its own `package.json`/`tsconfig.json`/build.

## History: one execution path, one merged agent

Two significant consolidations happened to get to today's shape, both worth knowing about if you're reading old code, old commits, or old docs:

1. **Legacy REST/SSE path removed.** There used to be a `POST /api/chat` path (`createAgent()`-based agents, a hand-rolled `goalService`/`router.ts`/`planner.ts`/`approval.ts` goal-tracking system) alongside the AG-UI/CopilotKit/LangGraph path. Once the React frontend moved to CopilotKit, nothing called the legacy path, so it was deleted. `src/router.ts`/`src/planner.ts`/`src/approval.ts` no longer exist.
2. **Three specialist agents (clockwork/research/qna) merged into one.** The three used to be separate LangGraph graphs (`clockworkGraph.ts`, `qnaGraph.ts`, `researchGraph.ts`), each its own tab in the UI, each with its own tool subset. They're now **one graph, `assistant`** (`src/graph/assistantGraph.ts`), with every tool available and the model deciding per-message what's appropriate — see "The assistant graph" below. `clockworkGraph.ts`, `qnaGraph.ts`, `src/agent.ts` (held `CLOCKWORK_SYSTEM_PROMPT`), and `src/agents/qnaAgent.ts` (held `QNA_SYSTEM_PROMPT`) were deleted as part of this — nothing imports them anymore. `researchGraph.ts` and `src/agents/researchAgent.ts` (`RESEARCH_SYSTEM_PROMPT`) were kept-but-unregistered (removed from `langgraph.json`) for a while as a reference implementation of step-by-step plan execution with per-step clarifying questions and a separate synthesis-approval gate, richer than what `assistantGraph.ts` does — but as part of the production cleanup pass they were confirmed to have zero real importers anywhere and were deleted outright. If that richer plan-execution shape is ever needed again, it'll have to be rebuilt from `assistantGraph.ts`'s current plan/HITL nodes (`planReviewNode` etc.) rather than revived from this history.
3. **The old synchronous "memory v1" pipeline has been removed outright.** It used to coexist with the async v2 pipeline behind a `MEMORY_V2_ENABLED` flag (default off, so v1 ran in production). As part of the production cleanup pass, v1 was deleted entirely and the former v2 pipeline is now the only one, unconditional — see "The memory pipeline" below for its current shape. Deleted with it: `src/memory/memoryService.ts` (`MemoryService`, backing `conversation_messages`/`semantic_memories`/`episodes`), `src/graph/executePersistence.ts` (`persistChatMemory`/`recordEpisodeForRun`/`extractPassiveFacts`), `src/memory/importanceScorer.ts`, `src/memory/classifier.ts`, `composePreferenceContext()` (was in `memoryTools.ts`), and the `recall_memory`/`get_similar_experiences`/`search_past_conversations` tools (they called `MemoryService` directly and were never ported to the v2 pipeline, so they were removed rather than left broken — the model's memory context is now injected automatically into every turn via `MemoryRetriever`, with no explicit recall tool). `conversation_messages`/`semantic_memories`/`episodes` are now fully orphaned collections — no code reads or writes them anymore; they were left in Mongo as historical data rather than migrated, consistent with how this repo already treated legacy collections in past consolidations. `config.ts`'s `memoryV2Enabled` flag is gone too; `memoryCaptureEnabled`/`memoryRetrievalEnabled` survive as independent master switches on the (now sole) pipeline.

What's still shared infrastructure regardless of any of the above:
- `src/agents/sharedTools.ts`'s `buildTools()` — the only way any graph gets MCP tools.
- `src/agents/shared.ts` — down to just `extractText()`/`DEFAULT_TENANT_ID` now (its `wrapWithConversationMemory()` was legacy-path-only and is gone).
- `src/memory/goalService.ts` — **no longer read-only.** `assistantGraph.ts` now persists every multi-step plan as a `GoalRecord` in the `goals` Mongo collection as soon as `plannerNode` decides `isMultiStep`, and drives it through `proposed → active → done`/`abandoned` from there (`proposeGoal`/`getProposedOrActiveGoal`/`approveGoal`/`updateSteps`/`completeCurrentStep`/`abandonGoal`). This makes goal progress durable across turns, threads, and server restarts — it is no longer just in-memory LangGraph thread state. `listActiveGoals()` (backing the `get_active_goals` memory tool) now returns real data. `checkGoalNode` looks up a proposed-or-active goal with a single query (`getProposedOrActiveGoal`) rather than two sequential ones, since at most one is ever expected per user.
- `src/graph/graphBootstrap.ts` — exports `ensureGraphReady()` (used by `assistantGraph.ts`'s `checkGoalNode`, the graph's first node, to connect to Mongo and ensure indexes exist before anything else touches the DB).

- `npm run dev` — compile in watch mode (does not restart the server itself, just recompiles)

- `npm run graph:dev` — starts `langgraphjs dev --port 2024`, hosting the single `assistant` graph (`server/langgraph.json`) for local development. **Must be running** for the AG-UI/CopilotKit path (`/api/copilotkit/*`) to work at all — `npm start` alone is not enough; see "Why two server processes" below.
- `node --env-file=.env dist/scripts/verifyAgUiStream.js <externalUserId> "<question>"` (after `npm run build`; also `npm run verify:agui -- <externalUserId> "<question>"`) — a standalone smoke test that runs the `assistant` graph directly through `@ag-ui/langgraph`'s `LangGraphAgent`, bypassing Express/CopilotKit entirely. Useful for isolating "is the graph itself broken" from "is the runtime/routing broken." It only drives a fresh run, not a resume — see "Manually resuming an interrupt" below for how to approve/reject/edit a plan from the command line.
- From `web/`: `npm run dev` (Vite dev server, `:5173`, proxies `/auth` and `/api` to `:3200`), `npm run build` (`tsc --noEmit && vite build`, outputs to `web/dist/`, which is what `server/`'s Express app serves in production).
- `npm run memory:provision-indexes` — one-off, privileged deployment step: creates the Atlas Search (`memory-items-text`) and Atlas Vector Search (`memory-items-vector`, 3072-dim `gemini-embedding-001`) indexes on `memory_items`. Requires MongoDB **Atlas**, not a plain self-hosted MongoDB — ordinary (non-Atlas-Search) v2 indexes are created automatically at every startup via `ensureMemoryV2Indexes()` and don't need this script.
- `npm run memory:verify` — checks that both Atlas Search indexes are `READY` and that a live Gemini embedding call succeeds. Run this (and confirm it passes) before every deploy — the memory pipeline depends on both.
- `npm run memory:migrate-taxonomy` — one-off, idempotent backfill for the memory taxonomy/lifecycle/provenance fields (`kind`+`subtype`, `version`, `supersededBy`, `provenance`, per-subtype `validTo`, revision `actorType`/`actorId`), the reliability-stage additions (`memory_events.nextAttemptAt`, `memory_items.embeddingAttempts`), and the episode-structure addition (`memory_items.episode` on every pre-existing episodic row, reconstructed from its source event where that event still exists). Required once after deploying any of these changes; safe to re-run repeatedly (every block is filtered on its own field being absent, so re-running after a later change gains a new backfill block is still a no-op for rows already migrated) and safe against a live DB (it only adds fields, never changes an item's value, status or canonical key). It also repairs the old supersession-direction bug by moving a superseded row's misused `supersedes` value into `supersededBy`. Run it **before** `memory:provision-indexes`, since the Atlas indexes now declare `subtype` as a filter/token field.
- `npm run memory:worker` — starts the standalone memory worker process (`src/scripts/runMemoryWorker.ts`), the third required leg of the deployment alongside `npm start` and `npm run graph:dev` (see "The memory pipeline" below). Independent process; connects to Mongo itself and polls forever.
- `npm test` (Vitest, `vitest run`) — unit tests only, 122 across thirteen files. Under `src/memory/v2/__tests__/`: `taxonomy.test.ts` (kind/subtype invariants, legacy mapping, TTL policy, scope enforcement), `repository.test.ts` (version chain, supersession direction, reinforce-vs-supersede, lifecycle expiry, rejection audit, lease reclaim, tenant isolation, backoff, embedding retry, listItems projection/pagination, episode-payload enforcement — run against the **real** `MemoryRepository` via the `inMemoryMongo.ts` collection double, which now also supports Mongo-shaped projections and a small `$match`/`$group`/`$sort`/`$limit` aggregation pipeline, not a fake that reimplements repository logic), `episodeBuilder.test.ts` (situation/objective/action/outcome/failure/resolution/lesson derivation, pure), `consolidator.test.ts` (capture/reinforce/supersede/reject decisions incl. secret refusal), `retriever.test.ts` (RRF fusion math, expiry filtering, token-budget enforcement, procedure-validation-status filtering), `procedurePolicy.test.ts` (promotion/demotion/rejection transitions, pure), `proceduralMemory.test.ts` (candidate creation, versioned promotion vs. in-place count updates, permanent-block-on-failure), `memoryWorker.test.ts` (per-event failure isolation via `processBatch()`'s dependency-injected mocks, structured episode payload attachment, graceful `requestStop()`), `metrics.test.ts` (counter registry), `policy.test.ts` (sensitivity + secret-pattern classification), `summarizer.test.ts` (profile-card generation). `src/memory/__tests__/memoryTools.test.ts` covers `remember_fact`'s secret-refusal/consent/write paths by mocking `interrupt()` and the repository. Shared record builders live in `v2/__tests__/fixtures.ts`. No integration/E2E suite exists, and no HTTP-level route tests do either (no `supertest`-equivalent harness in this repo) — the graph, thread ownership, and every route's request/response cycle are still uncovered.
- There is no `nodemon`/live-reload wired up for `dist/index.js` — after editing `.ts` you need a fresh `npm run build` (or a running `npm run dev` watch) *and* a server restart to see changes when running via `npm start`. The same applies to `npm run graph:dev` — it re-reads compiled/transpiled graph modules at its own startup, so a code change under `src/graph/` needs that process restarted too, independently of the main server. The `web/` side is different: since `server/`'s Express app just serves `web/dist/` as static files with no caching layer of its own, a `npm run build` in `web/` takes effect on the next browser page load with **no server restart needed**.
- **`server/.langgraph_api/`** (gitignored) is `langgraphjs dev`'s local persistent state — thread checkpoints, and critically, **every graph id ever registered under this dev server, even ones later removed from `langgraph.json`**. If you rename/remove a graph id, stale assistant registrations for the old id(s) linger here and will show up in `POST /assistants/search` results and confuse the separate LangSmith Studio UI (`https://smith.langchain.com/studio?baseUrl=http://localhost:2024`) with a "Graph '<old-id>' not found" error when it tries to load one. Stop `graph:dev`, `rm -rf .langgraph_api`, and restart to get a clean slate (this also discards all local thread history, so only do it in dev).

## Why two server processes (`:3200` and `:2024`)

`@ag-ui/langgraph`'s `LangGraphAgent` is a **client** of the LangGraph Platform API (thread creation/state/streaming-run endpoints) via `deploymentUrl` — it does not run a compiled graph in-process. `langgraphjs dev` is what implements that API locally. So `copilotRuntime.ts` (running inside the `:3200` Express process) makes HTTP calls to `localhost:2024` (or `LANGGRAPH_DEPLOYMENT_URL` if set) exactly the way it calls the MCP server on `:3100` — this is a structural consequence of the library's integration model, not a merge-able convenience split. It's also what gives every thread its persistence (messages, plan, pending interrupt) for free — `assistantGraph.ts`'s plan-review/HITL/resume behavior all relies on state the `:2024` process is keeping, not anything `:3200` stores itself.

`web/`'s Vite dev server (`:5173`) is unrelated to this and *is* just a convenience: production serves `web/dist/` directly from Express (`:3200`), no separate frontend process at all.

## Runtime dependencies

- **MongoDB** — required at startup (`connectDb()` in `src/db.ts`, idempotent — safe to call from multiple entry points; throws if it can't connect on the *first* call); stores users, memories, `thread_owners`, and `goals` (see `GoalService` below — `goals` is actively written to again). The `conversation_messages`/`episodes` collections still exist in the schema but nothing writes to them anymore. Default `mongodb://localhost:27017/`, db name `system1_chat_agent` (renamed from `chat_agent` during the memory-architecture rework, to identify the database by product name now that the same Atlas cluster/project may hold other databases). **Both** the `:3200` Express process and the `:2024` `langgraphjs dev` process connect to it independently — `assistantGraph.ts` calls `ensureGraphReady()` (from `src/graph/graphBootstrap.ts`) itself on first use, since it has no shared startup path with `index.ts` when hosted standalone by `langgraphjs dev`.
- **System1.MCP server** — required for any ClockWork tool call to work (`buildTools()`). `listMcpTools()` is called once at first use and cached, so if the MCP server isn't up yet when a request first triggers it, that failure isn't retried per-request — a restart is needed after bringing MCP up.
  - Account linking uses OAuth+PKCE against System1's IdP (`System1.MCP/src/oauthRoutes.ts`, `tokenClient.ts`), storing an encrypted refresh token per `externalUserId` in SQLite (`tokenStore.ts`). `getAccessToken()` in `tokenClient.ts` refreshes the access token transparently on every call; if the IdP rejects the refresh token itself (401, or 400 `invalid_grant` — i.e. it's expired/revoked, not a transient network failure), the stored refresh token is deleted (`unlink()`) and a `NotLinkedError` is thrown so the caller gets the normal re-link flow instead of a generic failure with a permanently-dead token left in the store.
  - `oauthRoutes.ts`'s `/oauth/link` handler trims trailing punctuation (`).,;:!?`) off the incoming `externalUserId` query param — defense against a client rendering the not-linked message's markdown link incorrectly and pulling a stray character into the URL, which would silently link the wrong id.
- **OpenRouter or Gemini** — the chat model provider. Selected via `MODEL_PROVIDER` env var (`"openrouter"` default, or `"gemini"`). `config.ts` throws at startup if the corresponding API key is missing.
  - Free-tier model slugs on both providers are unreliable in practice: OpenRouter's `:free` model list changes over time (query `GET https://openrouter.ai/api/v1/models` with your key to see what's actually still offered) and is capped at ~50 requests/day with zero account credit (429 `openrouter_free_tier_daily` once exhausted — add credits or wait for the daily reset). Some free models are also reasoning models that spend their entire token budget on hidden chain-of-thought before any real output — a bad fit for this app's small (300-500 token) internal-call budgets; prefer a plain instruct model. Gemini's free tier is model-specific and can be as low as 5 requests/minute (`gemini-2.5-flash`); `gemini-flash-lite-latest` has a much higher free quota and is a safer default than pinning an exact dated model name, since dated Gemini model ids get deprecated (404) over time. Since a single chat turn can fire several LLM calls (planning, main agent, memory tool calls), an aggressively-limited free model exhausts its quota almost immediately.
  - **Gemini-specific gotcha**: Gemini rejects any request whose final message is a model/assistant turn ("Requests ending with a model turn are not supported"). Keep this in mind before adding any direct `model.invoke(messages, config)` call on a message list that might end in an AI message — append a trailing `HumanMessage` instruction instead of relying on the system prompt alone.
- **LangSmith tracing (optional)** — `LANGCHAIN_TRACING_V2=true` + `LANGCHAIN_API_KEY` + `LANGCHAIN_PROJECT` in `.env`, picked up automatically by LangChain/LangGraph on both `:3200` and `:2024` (`langgraph.json`'s `"env": ".env"` points the graph process at the same file). No code wiring needed beyond the env vars.

### Auth (`src/auth.ts`, `src/db.ts`)

Cookie-based JWT sessions, no refresh-token flow — a single 7-day-TTL JWT (`jwt.sign({sub: userId}, ..., {expiresIn: SESSION_TTL_SECONDS})`) stored in an `httpOnly`, `sameSite: "lax"` cookie named `session`. `requireAuth` re-validates the user still exists in Mongo on every request (not just JWT signature/expiry) via `findUserById`, so a deleted user is deauthenticated immediately even with a still-valid token. Passwords are bcrypt-hashed (cost factor 10) in `createUser`; there's no password-reset or email-verification flow. `/auth/me` never 401s — it always returns 200 with `{authenticated: boolean, ...}`, distinct from every other route which 401s via `requireAuth`. `requireAuth`/`registerAuthRoutes` is the only Express-side auth middleware mounted directly in `index.ts` (there's no other route left — `/api/chat` is gone) — the AG-UI path reaches the same session cookie independently, since `copilotRuntime.ts` re-implements the cookie-parsing + JWT-verify logic itself (see below) as it operates on a raw fetch `Request`, not an Express `req` with `cookie-parser` middleware already run.

## Architecture: the AG-UI/CopilotKit/LangGraph path

### The assistant graph (`src/graph/assistantGraph.ts`)

One LangGraph `StateGraph`, registered as `"assistant"` in `langgraph.json` — the only graph currently hosted. Its multi-step plans are **durable goals**, persisted in Mongo (`GoalRecord`, `src/memory/goalService.ts`) rather than living only in this run's LangGraph thread state — see "Durable goals" below for why. Shape:

```
START -> checkGoal
checkGoal --routeAfterCheckGoal-->
  "planReview"  (a proposed GoalRecord already exists for this user - re-present it for approval)
  "execute"     (an active GoalRecord exists - work its current step)
  "planner"     (no goal on file - decide isMultiStep fresh)
planner --routeAfterPlanner-->
  "execute"     (not multi-step - handle directly, no approval friction)
  "planReview"  (multi-step - a GoalRecord was just proposed; pause for approval first)
planReview [interrupt: plan_edit] --routeAfterPlanReview-->
  "execute"  (approved or edited - GoalRecord flipped to "active")
  END        (rejected - GoalRecord abandoned, cancellation message appended)
execute -> END
```

- **`checkGoalNode`** — looks up a `proposed`/`active` `GoalRecord` for this `externalUserId` in Mongo, by user id, not by thread — this is what makes goal progress survive a page reload into a new thread, or a server restart, not just the current LangGraph run's in-memory state. Sets `goalPhase` (routing-only) plus `plan`/`goalId` derived from whatever it found; all three come back `null` if there's nothing on file. **Calls `ensureGraphReady()` itself, first thing** — it's the *first* node in the graph now (`START -> checkGoal`), so when hosted standalone by `langgraphjs dev` nothing else has connected to Mongo yet at that point; every other node used to reach the DB lazily via `resolveContext()` inside `executeNode`, which ran later. Without this, every run crashes with `Database not connected - call connectDb() before using it.` the instant `checkGoalNode` calls `goalService`.
- **`plannerNode`** — decides `isMultiStep` for the newest user message via `silentJsonCompletion()` (see "Structured decisions that must never appear as chat output" below), not a LangChain `ChatModel` call. A single question, a single action, or a short follow-up is *not* multi-step, even if it needs a couple of tool calls — only genuinely multi-part requests (several distinct actions/investigations, or one broad request that naturally splits into ordered sub-steps) get a plan. When it decides multi-step, it immediately calls `goalService.proposeGoal()` to persist a `GoalRecord` (status `"proposed"`) before ever pausing for approval. On any error, or if the model says multi-step with fewer than 2 steps, falls back to `plan: null`/`goalId: null` (handle directly) rather than blocking the turn.
- **`planReviewNode`** — `interrupt()`s with `{type: "plan_edit", id, plan}` (the same `AgentInteraction`/`ResearchPlan` shapes the now-deleted `researchGraph.ts` originally established, reused verbatim so the frontend's existing plan-editor UI works unchanged). Resume value: `{action: "approve"} | {action: "update", plan: ResearchPlan} | {action: "reject"}`. Reject calls `goalService.abandonGoal()` and appends a cancellation `AIMessage`; approve/update calls `goalService.approveGoal()` (update also calls `updateSteps()` first) and falls through to `execute`.
- **`executeNode`** — when there's no `goalId` (a plain single-shot request), runs the same model-call/tool-execution ReAct loop (`runReactLoop`, `MAX_TOOL_ITERATIONS = 6`) as before and clears `plan`/`goalId`. When there **is** a `goalId`, it deliberately runs only the goal's *current* step — one step per user turn, not the whole plan in one pass — then calls `goalService.completeCurrentStep()` to advance it in Mongo. If that was the last step the goal is marked `"done"` and `plan`/`goalId` are cleared; otherwise they're left as-is, because `checkGoalNode` will pick the goal back up from Mongo on whatever the user's *next* message turns out to be, regardless of its content — this mirrors how the original (deleted) `router.ts`/`goalService` REST-path behaved with an in-progress goal.
- The `ASSISTANT_SYSTEM_PROMPT` constant (`src/assistantPrompt.ts`) folds together what used to be three separate agent prompts (act-immediately-on-actions, check-memory-before-research, answer-directly-for-simple-questions) plus an explicit decision preamble, since one model now has every tool and must pick what's appropriate itself rather than being scoped to one specialist role.

### Durable goals (`src/memory/goalService.ts`, `src/memory/types.ts`)

A `GoalRecord` (`{id, tenantId, userId, title, status, steps, currentStepIndex, createdAt, updatedAt}`, status `"proposed" | "active" | "done" | "abandoned"`) is the durable, cross-turn/cross-thread/cross-restart representation of a multi-step plan — the LangGraph thread-state `plan`/`goalId` fields in `assistantGraph.ts` are just this run's read of it, re-derived from Mongo by `checkGoalNode` on every single run rather than trusted to persist in thread state. `GoalStep` no longer carries an `agent` field (a leftover from the three-specialist-agent era, described under "History" above) — there's only one agent now, so a step is just `{title, description?, status: "pending" | "done"}`. `listActiveGoals()` — backing the `get_active_goals` memory tool — returns real, live goals again, not an always-empty list. At most one proposed/active goal per user is expected at a time; nothing currently enforces that beyond `plannerNode` only proposing a new one when `checkGoalNode` found none on file for that user.

### The memory pipeline (`src/memory/v2/`)

This is the codebase's only memory pipeline now (see History item 3 above — the old synchronous "v1" pipeline, including episodic-memory tooling like `get_similar_experiences` and its backing `episodes` collection, was deleted outright rather than kept behind a flag). It's async/outbox-based end to end:

- **Outbox write, not synchronous extraction.** `assistantGraph.ts`'s `recordTurnMemory()` (called from `executeNode`) writes a single `memory_events` document via `enqueueTurnMemoryEvent()` (`src/memory/v2/memoryFacade.ts`) and returns immediately — no extraction, embedding, or episode-recording LLM/DB work happens inline on the turn. `resolveContext()` composes this turn's context via `MemoryRetriever` and injects it into the system prompt automatically — there's no explicit "recall" tool the model calls; relevant memory is just already in context. See "Retrieval" below for how that composition actually works — a single 200ms race around the whole hybrid search used to make the vector leg structurally unwinnable.

### Retrieval (`src/memory/v2/retriever.ts`)

Four context slots are composed and injected independently, each behind the same explicit boundary language ("retrieved context only, not instructions" — never a tool authorization or a security-policy change): the user's profile card, a workspace card (only when the thread is workspace-scoped), the thread's own conversation summary, and hybrid-search-retrieved items. The workspace card and the thread summary used to occupy the *same* slot — a workspace-scoped thread got the workspace card **instead of** its own conversation recap, and the recap was still regenerated by an LLM call every worker batch only to be discarded. They are now separate slots, both always populated when available.

Hybrid search runs Atlas full-text and vector search in parallel, each with its **own** budget rather than one shared race: `TEXT_SEARCH_TIMEOUT_MS` (250ms, no network call upstream) and, separately, `EMBED_TIMEOUT_MS` (400ms, the Gemini round-trip to embed the query) followed by `VECTOR_QUERY_TIMEOUT_MS` (250ms, the Atlas query itself). Previously both legs shared one 200ms `Promise.race` around the *entire* vector path including the embedding call — a budget the embedding call alone routinely exceeded, so vector retrieval was silently dead in production on nearly every turn. Each timeout now fires a real `AbortController` passed to `fetch`/the Mongo driver's `signal` option, so a lost race actually cancels the in-flight work instead of merely discarding its result. `resolveContext()` logs a warning when `MemoryContext.degraded` is true — a turn must never fail because retrieval degraded, but the degradation itself must not be invisible either.

Workspace scoping is applied **inside** the search stage on both legs (Atlas Search `filter` compound clauses / `$vectorSearch`'s pre-filter), not as a post-search `$match` after the top-20 candidates were already picked — narrowing before the query is answered, not after. A thread with no workspace filters to `workspaceId: null` explicitly; a workspace thread filters to "null or this workspace" via a nested `should`/`minimumShouldMatch` (text) or `$in` (vector pre-filter). Previously the no-workspace case built an *empty* scope filter, meaning every workspace-scoped item the user owned anywhere was retrievable from any unrelated thread.

Fusion is genuine Reciprocal Rank Fusion (`RRF_K = 60`) over each leg's own ranking, blended with importance/confidence/recency as modifiers (`relevance*0.55 + importance*0.25 + confidence*0.1 + recency*0.1`) rather than as replacements for it. Previously neither leg's Atlas relevance score was even projected — search hits were concatenated, de-duplicated, and sorted purely on stored metadata, so an exact match could rank below an unrelated item that merely had higher importance.
- **The worker** (`src/memory/v2/memoryWorker.ts`, run via `npm run memory:worker` as its own process — never inside `index.ts` or `graph:dev`) polls `memory_events`, batches per user/thread (flush at 3 turns or the oldest event turning 5 minutes old, capped at 10 events/12k chars), and runs extraction (`MemoryExtractor`, an LLM call via `silentJsonCompletion()`) → policy (`MemoryPolicy`, deterministic sensitive-data keyword/pattern gate) → consolidation (`MemoryConsolidator`, canonical-key merge/supersede into `memory_items`, with a `memory_revisions` audit row on every change) → embedding (`embedTextBatch()` in `src/memory/embeddings.ts`) → episode creation (only for tool-using turns, goal steps, or failures — never a plain Q&A) → summary refresh (`MemorySummarizer`, `src/memory/v2/summarizer.ts` — an LLM-synthesized rolling recap per thread via `silentJsonCompletion()`, plus a no-LLM bullet card per user/workspace built from the top-importance active `memory_items`; both write to `memory_summaries`, which `MemoryRetriever` reads). Per-user/thread leases (`memory_worker_locks`) plus per-event lease fields on `memory_events` make this safe to run as multiple replicas.
- **`remember_fact`** (`src/memory/memoryTools.ts`, the only tool `buildMemoryTools()` still returns) classifies the candidate fact via `MemoryPolicy`; a non-sensitive one is written immediately to `memory_items` (`embeddingStatus: "pending"`, picked up by the worker's embedding pass), while a sensitive one `interrupt()`s with a `memory_consent` `AgentInteraction` (`src/graph/interactionTypes.ts`, rendered by `web/src/InteractionRenderer.tsx`'s `MemoryConsentInteraction`) and writes nothing until the user approves. It writes at `kind: "semantic"` with an optional `subtype` of `fact` (default) or `preference`, and carries `provenance.sourceType: "explicit_tool"` / `actorType: "user"` — which is what lets consolidation treat it as outranking worker inference (see the taxonomy section below).

### The memory taxonomy and lifecycle (`src/memory/v2/taxonomy.ts`)

`taxonomy.ts` is the single source of truth for what memory exists, where it may live, and how long it lives. Three things are defined there and nowhere else:

- **Kind vs. subtype.** `kind` is the memory category (`semantic` | `episodic` | `procedural`); `subtype` is the member. Semantic subtypes are `fact` | `preference` | `entity` | `relationship` | `stable_context`; episodic has `episode`; procedural has `procedure`. **Factual memory is a subtype of semantic memory, not its own store** — one `memory_items` collection holds every kind, distinguished by these two fields. This replaced a flat `kind: "preference" | "fact" | "episode"` enum that mixed a category with its members. `resolveLegacyKind()` maps the old values forward and is used by both the migration script and any read path that meets an un-migrated row.
- **Scope policy.** `assertValidTaxonomy(kind, subtype, scope)` runs inside `upsertByCanonicalKey`, i.e. on the one write path both the worker and `remember_fact` share, so an invalid combination cannot be persisted by either. **The application decides scope, never the model** — an extraction candidate has no scope field at all; the worker derives it from the originating thread's workspace assignment. Semantic and episodic memory may be `user`- or `workspace`-scoped; procedural is `workspace`-only (a procedure is a shared asset, not a personal preference). The wider SYSTEM/TENANT/THREAD hierarchy is deliberately *not* modelled yet: every retrieval path filters by `userId`, so a tenant-scoped item could be written and never read. That arrives with procedural memory, which is the first kind that needs a shared scope.
- **TTL by subtype.** `expiresAtFor(subtype)` assigns `validTo` at write time. Everything semantic and procedural gets `null` (no automatic expiry) on purpose — a timezone or a preference stops being true when it *changes*, which consolidation already handles, and silently ageing out a still-correct fact is worse than keeping it. Only `episode` carries a TTL (365 days), because an episode records one past interaction whose usefulness genuinely decays. **The worker's lifecycle sweep** (`expireStaleItems`, run hourly via `sweepExpiredIfDue()`, capped at 200 items per run) moves expired items from `active` to the new `expired` status and writes an `expired` revision for each. Note this sweeps `memory_items` only — nothing expires *thread* rows, and a `memoryMode: "temporary"` thread persists until explicitly ended (it is hidden from `GET /api/threads`, which is what makes that acceptable).

**Versioning.** `MemoryItemRecord` carries `version` (monotonic under a canonical key), `supersedes` (backward pointer, never rewritten after insert) and `supersededBy` (forward pointer, set on the *old* item when it is replaced). The two directions are separate fields because a single field used for both collapses the chain: `supersedeItem` previously wrote the successor id into the old item's `supersedes`, clobbering its link to its own predecessor and making history unwalkable past one hop. `repository.test.ts` regression-tests this against the real repository method — the earlier test suite could not catch it because its fake repo reimplemented the method under test.

**Consolidation outcomes** are now three, where they used to be conflated into one: `created` (nothing on file), `updated` (the value changed, so a new version supersedes the old), and `reinforced` (the *same* value restated — `reinforceItem` raises confidence/importance in place, never lowering them, merges source event ids and extends the expiry window, rather than growing an unbounded insert/supersede chain describing a value that never moved). A lower-confidence *contradiction* from extraction is refused; the same contradiction via `remember_fact` is accepted, because the user is the authority on their own facts. The policy gate runs before all of this, so a sub-threshold or sensitive candidate never reaches the reinforce path and cannot extend a stored memory's life on weak evidence.

**Provenance.** Every item carries a `provenance` object answering "why does the system believe this": `sourceType` (`extraction` | `explicit_tool` | `user_edit`), `actorType`/`actorId`, `sourceThreadId`, `sourceGoalId`, `sourceTurnIds`, `extractedAt`, `extractionModel` (the resolved provider model id, via `silentModelId()`) and `extractionVersion` (`EXTRACTOR_VERSION` in `extractor.ts`, bumped whenever that prompt/schema changes). The extractor now returns a `sourceTurn` per candidate so the worker attributes an item to the single turn that stated it; previously every candidate claimed all ten of the batch's events as sources. `sourceEventIds` deliberately stays a **top-level** field rather than moving inside `provenance` — it backs both a Mongo index and the source-aware thread-deletion cleanup, and relocating it would mean rewriting a working deletion path for no functional gain.

**Audit.** `memory_revisions` gained `actorType`/`actorId` and four operations (`expired`, `restored`, `merged`, `rejected`). `recordRejection()` writes a `rejected` row with `itemId: null` whenever the policy gate refuses a candidate — previously a refused sensitive fact left no trace at all, which is exactly the case an operator most needs to review. Rejections are only reachable by action, hence the `{tenantId, userId, action, createdAt}` index.

### Episodic memory (`src/memory/v2/episodeBuilder.ts`)

An episode is a `memory_items` row with `kind: "episodic"`, `subtype: "episode"`, carrying an `episode: EpisodeDetails` payload — `situation`, `objective`, `action` (the tool sequence actually invoked), `outcome`, `failed`/`failedTool`, `resolution`, `lesson`, `goalId`/`stepIndex`. `upsertByCanonicalKey` enforces this the same way it enforces `procedure` for procedural items: a `kind: "episodic"` write with no `episode` payload throws.

**This replaced a bare `content: event.assistantText`** — an episode used to be a copy of the assistant's final reply with no structure behind it at all, which was Episodic memory's correctness ceiling (the taxonomy work gave every kind a *place* to live, but never gave episodes a *shape*). `buildEpisodeDetails()` (`episodeBuilder.ts`) derives the structure **deterministically from the triggering `MemoryEventRecord`** — no LLM call, matching the pipeline's existing cost-control principle (extraction is the only LLM-in-the-loop step; this is a plain function of `userText`/`assistantText`/`toolSummaries`/`goalId` already on hand):

- `situation`/`outcome` are the user's message and the assistant's final reply, truncated to 400 chars each.
- `objective` distinguishes a goal-step episode ("Complete step N of an active multi-step goal") from a standalone request.
- `action` is the ordered tool-name sequence from `toolSummaries`.
- `failed`/`failedTool` come from the first `toolSummaries` entry with `status: "error"`.
- `resolution` is populated only when a *later* tool call in the same turn succeeded after an earlier one failed — a success that happened *before* the failure is never mistaken for a fix.
- `lesson` is deliberately conservative: populated for a recovered failure, an unrecovered failure, a multi-tool success, or a completed goal step — left `null` for a plain single-tool success, since there's nothing to generalize from one clean call. Fabricating a "lesson" from an ordinary success would be worse than having none.

`content` (what full-text search and the profile/summary cards actually read) is now `episodeContent(episode)` — a one-line synthesis of `situation -> outcome (lesson)` built *from* the structured fields, not a second independent summary that could drift from them.

`memory:migrate-taxonomy` backfills `episode` onto pre-existing episodic rows: it looks up the original `MemoryEventRecord` via the item's `sourceEventIds[0]` and reruns `buildEpisodeDetails()` against it when that event still exists, or falls back to a minimal, honestly-labeled reconstruction (`situation`/`objective`: `"unknown - source event no longer exists"`) when the source event has already been cleaned up (e.g. by thread deletion) — never fabricating detail that was never observed.

### Procedural memory (`src/memory/v2/proceduralMemory.ts`, `procedurePolicy.ts`)

Implements the promotion pipeline: `Episode -> Candidate Procedure -> Validation -> Active Procedure`. Not a separate storage system — every procedure is a `memory_items` row with `kind: "procedural"`, `subtype: "procedure"`, carrying a `procedure: ProcedureDetails` payload (`steps`, `successCount`, `failureCount`, `validationStatus`). Confined to `workspace` scope by `taxonomy.ts` — a procedure is a shared, reusable asset, not a personal one — so a user-scoped thread (no workspace assigned) never contributes candidates at all. This is a deliberate limitation: without it, "how this one person happened to do something once" would masquerade as a validated, shareable procedure.

**Signal**: `memoryWorker.ts`'s episode loop, for any episode-worthy event with two or more tool calls, derives a tool-name sequence (e.g. `start_time_entry > stop_time_entry`) and calls `proceduralMemoryService.recordOutcome()`. This is deliberately deterministic, not another LLM call — matching Phase 26's cost-control principle, and there's no natural-language "how" beyond the literal tool sequence the pipeline can currently observe and verify success/failure against.

**Governance** (`procedurePolicy.ts`'s `evaluateProcedureStatus()`, pure and unit-tested, no I/O): a brand-new sequence's *first* observation must succeed or nothing is written at all (a pattern that has only ever failed once is not "candidate" evidence, it's just a failure). From `candidate`, promotion to `active` requires `successCount >= MIN_SUCCESSES_FOR_PROMOTION` (3) **and** `failureCount === 0` — a single recorded failure blocks promotion permanently for that version, however many further successes accumulate, since "repeated success" means an unbroken record, not a majority. `rejected` is terminal — a pattern that failed enough times with zero successes (`MAX_FAILURES_WITH_NO_SUCCESS`, 2) doesn't get evaluated back toward candidacy; un-rejecting one would need a deliberate out-of-band edit. An `active` procedure that starts failing as often as it succeeds is demoted to `deprecated` (not deleted — the environment may have changed, not the procedure), and can only earn its way back to `active` by clearing the same promotion bar again with a clean record since.

**Writes**: a governance-status change (promotion/demotion/rejection) goes through the same `upsertByCanonicalKey` supersession path as facts — creating a new version, so a rollback can point at exactly the version where a procedure was promoted or demoted, not just "sometime after count N." A bare count increment that doesn't change status uses `MemoryRepository.updateProcedureCounts()` instead — mutates in place, still writes a `consolidated` revision, but doesn't grow the version chain for every single observed run.

Human approval (spec Phase 8's "+ optional human approval") is **not implemented** — promotion today is fully automatic once the deterministic policy is satisfied. Adding an approval gate would need a new `AgentInteraction` variant and frontend rendering (`InteractionRenderer.tsx`), which is real, separate work; noted here rather than silently left out of the picture.

### Reliability & security hardening

A dedicated pass over the outbox/worker/API surface, closing gaps the Phase 1 audit found and nothing earlier in this rework had touched:

- **A crashed worker no longer strands events forever.** `"processing"` used to be written once (on lease) and read by nothing — a worker killed mid-batch left its events there permanently, with no reaper. `MemoryRepository`'s private `eligibilityFilter()` now matches *either* a fresh/backoff-cleared `"pending"` event *or* a `"processing"` one whose `leaseExpiresAt` has passed, and `findEligibleGroup`/`leaseEventsForGroup` both use it — so a stranded lease is picked back up by the next tick that looks. `repository.test.ts` seeds an expired-lease "processing" row directly and asserts it's reclaimed.
- **The outbox write is now durably awaited.** `executeNode`'s `persistTurnMemory()` (renamed from `fireRecordTurnMemory`) is `await`ed on the graph's completion path instead of fired-and-forgotten — a crash between the graph "finishing" and that promise settling used to lose the turn's memory event permanently, with nothing durable ever written to retry. Still never fails the turn (same catch-and-log contract as before); only the timing changed. Costs one indexed insert's latency, not a model call's — everything expensive stays in the async worker.
- **Failed events back off instead of retrying instantly.** `MemoryEventRecord` gained `nextAttemptAt`; `failEvent()` sets it via exponential backoff (30s → 2m → 8m → 32m, capped at 30min) instead of clearing straight back to immediately-eligible. Previously a failed event (and, see below, every other event batched with it) was re-eligible on the very next poll, so one poison event could burn all five attempts within seconds.
- **A single bad event no longer dead-letters its whole batch.** `processBatch()`'s per-candidate and per-event consolidation calls are now each wrapped in their own try/catch, accumulating a `failedEventIds` set — `markEventsDone()` is called with only the events that actually succeeded, and `failEvent()` is called individually for the ones that didn't. The old design caught any error at the batch level and dead-lettered every event in it together. `memoryWorker.test.ts` calls the (still-private) `processBatch()` directly via dependency-injected mocks and asserts one poisoned event doesn't take healthy ones down with it.
- **An embedding failure is retried, not permanent.** `MemoryItemRecord` gained `embeddingAttempts`. `setEmbedding()` now only moves `embeddingStatus` to the terminal `"failed"` after `MAX_EMBEDDING_ATTEMPTS` (5) *consecutive* failures — a transient failure leaves it at `"pending"`, which `listPendingEmbeddings()` already selects, so it retries automatically on the worker's next `embedPendingItems()` pass with no new query needed.
- **The worker shuts down gracefully.** `MemoryWorker.requestStop()` sets a flag `runForever()`'s loop checks between ticks (never mid-batch — an in-flight batch always finishes or fails through the normal per-event path first). `runMemoryWorker.ts` installs `SIGTERM`/`SIGINT` handlers that call it, so an ordinary container restart/redeploy no longer kills the process mid-batch and manufactures the stranded-lease condition the first bullet now separately recovers from anyway.
- **Worker queries are explicitly tenant-scoped.** `findEligibleGroup`/`leaseEventsForGroup`/`acquireLock`/`releaseLock` all take a real `tenantId` now, threaded from `MemoryWorker.tick(tenantId)` — previously the lease/group aggregation had no tenant filter at all and the lock calls used a hardcoded `DEFAULT_TENANT_ID` regardless of which tenant's events were actually being processed. `runForever(pollIntervalMs, tenantIds)` polls a list of tenants once per cycle (just `[DEFAULT_TENANT_ID]` today) rather than assuming a single one structurally. `repository.test.ts` seeds two tenants under a colliding `userId` and asserts they're never grouped together.
- **Secrets are refused outright, not merely consent-gated.** `MemoryPolicy.classify()` (`policy.ts`) gained a `"secret"` sensitivity tier — API key prefixes (OpenAI/Anthropic/AWS/GitHub/Slack shapes), PEM private-key blocks, JWTs, and connection strings with embedded credentials — checked separately from the (lowercased) sensitive-topic keywords since these patterns are case-sensitive token shapes. Unlike `"sensitive"` content (a health fact a user might deliberately choose to remember), a `"secret"` never reaches `remember_fact`'s `interrupt()`/consent flow at all — `memoryTools.ts` refuses it immediately with a fixed message and records the refusal via `recordRejection()`. The worker-extraction path is already blocked identically by `canAutoCapture()`'s existing `sensitivity !== "none"` gate; the new tier is about *distinguishing* a secret from merely-sensitive content for the explicit-tool path's outright-refusal behavior, not about blocking it twice.
- **Lightweight observability**: `src/memory/v2/metrics.ts` is an in-process counter registry — deliberately not a Prometheus/OTel client, since nothing else in this repo exports metrics and a framework for one subsystem would be its own unnecessary infrastructure. Wired into the outbox (`enqueueEvent`/`markEventsDone`/`failEvent`), consolidation (`consolidation_created`/`updated`/`reinforced`/`skipped_secret`/`skipped_sensitive`/`skipped_low_confidence`/`errors`), and embedding (`embeddings_permanently_failed`). `MemoryWorker.runForever()` logs a snapshot every 60s as a heartbeat (`console.log`, not a new API surface — see the gap noted below). `turnId` (already on every event/item/provenance) remains this pipeline's correlation id end to end; a second, parallel identifier was deliberately not introduced.
- **The memories API no longer over-exposes or under-validates.** `MemoryRepository.listItems()` now projects away `embedding` (previously ~3072 floats per item shipped straight to the browser) and is paginated (`limit`, capped at 200; a `before` cursor on `updatedAt`) — `GET /api/memories` returns `{ items, nextCursor }`. `PATCH /api/memories/:id`'s `importance` is clamped to `[0, 1]` and a non-finite value now 400s, rather than passing straight through into the field that dominates retrieval ranking and the profile card's sort key.

**What this pass did not build**: a metrics/health HTTP endpoint (queue depth, dead-event count) — there's no admin/role concept in this codebase to gate it behind, and exposing cross-user aggregate counts on an ordinary authenticated route would be a new, narrow security surface for its own sake; the heartbeat log is the honest scope-limited alternative. And still nothing exercises the routes themselves at the HTTP level (no `supertest`-equivalent test harness exists in this repo, and adding one is a real, separate infrastructure decision) — the fixes above (embedding projection, importance clamping) are tested against `MemoryRepository` and the route's own validation logic directly, not through an actual HTTP request/response cycle.

- **Goal tools are split from memory tools** (`buildGoalTools()` vs. `buildMemoryTools()` in `memoryTools.ts`) — `get_active_goals` stays available even when memory is paused/temporary, since a durable goal is orthogonal to memory capture.
- **Workspaces and temporary chats**: `ThreadRecord` carries `workspaceId`/`memoryMode` fields (`src/memory/types.ts`); `getThreadMemorySettings()`/`setThreadWorkspace()`/`setThreadMemoryMode()` (`src/threadOwnership.ts`) are the read/write paths `resolveContext()`/`recordTurnMemory()` use every turn. A `memoryMode: "temporary"` thread skips memory entirely (no event, no retrieval, no tools) and is excluded from `GET /api/threads`'s list — the frontend's "Temporary chat" button (`ChatView.tsx`) creates one and shows an "End temporary chat" banner that flips it back to normal.
- **APIs**: `GET/PUT /api/memory/settings` (global per-user on/off, `src/memory/v2/memorySettingsRoutes.ts`/`memorySettingsService.ts` — checked by both `resolveContext()` and `recordTurnMemory()`), `GET/PATCH/DELETE /api/memories` (`memoriesRoutes.ts`), `GET/POST/PATCH/DELETE /api/workspaces` (`workspaceRoutes.ts`/`workspaceService.ts`). Thread deletion (`threads.ts`) also calls `memoryRepository.deleteEventsAndCleanupForThread()` — removes the thread's own `memory_events` and strips/deletes any `memory_items` whose only source was one of them. Workspace deletion purges workspace-scoped items/summaries and unassigns (not deletes) affected threads.
- **Deployment is now mandatory, not opt-in**: `npm run memory:provision-indexes` (one-off, requires Atlas) and `npm run memory:verify` (index-readiness + live embedding check) must pass before deploy — see the Commands section. Three independent processes are required: `npm start` (Express `:3200`), `npm run graph:dev` (LangGraph `:2024`), `npm run memory:worker`.
- `findSimilarEpisodes`-equivalent lookups (used internally by episode creation above) only do real semantic similarity when `embedText()` (`src/memory/embeddings.ts`) actually succeeds - **specifically requires `GEMINI_API_KEY`, independent of `MODEL_PROVIDER`** (it calls Gemini's `embedContent` REST endpoint directly, with its own hardcoded model id, regardless of which provider the chat model itself uses).
- **Real bug hit in practice**: `EMBEDDING_MODEL` was once hardcoded to `"text-embedding-004"`, which 404s ("is not found for API version v1beta, or is not supported for embedContent") even with a valid `GEMINI_API_KEY` configured - Gemini's embedding model ids get deprecated/renamed the same way dated chat model ids do (the `gemini-flash-lite-latest`-vs-pinned-ids note elsewhere in this doc is the same failure mode, just for a different endpoint). `embedText()`'s `catch` swallows this silently and returns `null`, so the symptom looks identical to "no key configured" - always double check `GET /v1beta/models?key=...` filtered to `supportedGenerationMethods` including `embedContent` before assuming a `null` embedding means a missing key. Fixed by switching to `"gemini-embedding-001"` (confirmed working, 3072-dim). If this 404s again in the future, re-run that same models query to find the current replacement.
- **Gotcha to remember if you touch message-type checks in this pipeline**: don't reach for `instanceof AIMessage`/`instanceof ToolMessage` on anything that came out of a model call rather than being constructed directly with `new ToolMessage(...)`. What `model.bindTools(...).invoke()` actually returns is `AIMessageChunk`, a sibling class, not a subclass, in this `@langchain/core` version — `instanceof AIMessage` is silently `false` for it. Use `message.getType() === "ai"` (and `"tool"` for the equivalent check) instead, which works correctly on both the full class and its chunk variant.

### Structured decisions that must never appear as chat output (`src/silentModel.ts`)

`plannerNode`'s `isMultiStep` decision is **not** made via a LangChain `ChatModel`/`Runnable` — it's a raw `fetch()` to the provider (OpenRouter's `/chat/completions` with `response_format: {type: "json_object"}`, or Gemini's `generateContent` with `responseMimeType: "application/json"`), parsed with a Zod schema. This was forced by a real, reproducible bug: LangGraph's message-streaming (what turns model output into AG-UI `TEXT_MESSAGE_*` events, i.e. visible chat text) hooks into LangChain's *callback* system, and any `ChatModel.invoke()` call happening inside a graph node — even one explicitly tagged `"langsmith:nostream"` (the documented LangGraph mechanism for excluding a call from message-streaming), tried both via the invoke-time `config.tags` and via `.withConfig({tags: [...]})` bound on the model — still leaked its raw JSON into the chat as a garbled message before the plan-approval UI ever rendered. A plain `fetch()` has no LangChain Runnable/callback involvement at all, so there's nothing for that streaming machinery to capture. Use `silentJsonCompletion()` for any future internal/non-conversational model decision inside a graph node; don't reach for a tagged `ChatModel` call expecting it to actually suppress streaming in this stack. (The now-deleted `researchGraph.ts`'s `plannerNode`/`clarifyStepNode` used the tagged-`ChatModel` approach and never had this leak fixed — if that graph's plan-execution shape is ever rebuilt, don't copy that part of it.)

### The generic interaction model (`src/graph/interactionTypes.ts`)

One `AgentInteraction` discriminated union (`"approval" | "question" | "plan_edit"`) backs every `interrupt()` call site (currently only `plan_edit`, from `assistantGraph.ts`'s `planReviewNode` — the now-deleted `researchGraph.ts` was the only other user of the other two variants). The frontend has its own structurally-identical copy in `web/src/interactionTypes.ts` (kept in sync by hand, not shared via a package — there's no shared-types package in this repo) and renders all three variants through one `useInterrupt()` call (`web/src/InteractionRenderer.tsx`).

**The exact shape of `event.value` inside `useInterrupt`'s `render` callback depends on which of two independent delivery paths fired, and neither is "just the payload" — this took real debugging effort to pin down, don't re-derive it from first principles:**
- **Legacy path** (`on_interrupt` custom event): `event.value` is a **JSON-encoded string** of the `AgentInteraction`, not a parsed object. The pre-parsed object lives on that event's `rawEvent` field — which `copilotRuntime.ts`'s `sanitizeEvents()` deliberately strips from *every* event before it reaches the browser (it also carries this graph's system prompt text verbatim). So only the string form ever survives to the client; it must be `JSON.parse()`'d.
- **Standard AG-UI path** (a `RUN_FINISHED` event with `outcome: "interrupt"` — what `langgraphjs dev` actually emits in this stack): `event.value` is the **unwrapped LangGraph `Interrupt` object**, `{ id, value: <AgentInteraction> }` — one level of wrapping around the real payload, not the payload itself.

`InteractionRenderer.tsx`'s render callback normalizes both (parse-if-string, then unwrap-if-`{id, value}`-shaped) before ever touching `.type`/`.plan`/etc. An earlier version of this code assumed `event.value` was always the flat payload and crashed with `Cannot read properties of undefined (reading 'steps')` — because on the standard path it was reading the `{id, value}` wrapper's nonexistent `.plan`, and there was no `else` case, so a mismatched shape fell straight into rendering `PlanEditInteraction` with garbage. Keep the explicit `type`+field checks (not an unguarded `else`-fallback) if you touch this file again.

### CopilotKit runtime (`src/copilotRuntime.ts`)

- **`buildCopilotAgents({request})`** is the `AgentsFactory` CopilotKit's v2 runtime calls per request. It resolves the caller's session from the raw `Cookie` header itself (Express's `cookie-parser` middleware never runs on this bridged fetch `Request`) and returns one `OwnedLangGraphAgent` for the single `"assistant"` graph id (`AGENT_GRAPH_IDS`, must match `langgraph.json`'s key and the React app's `agentId` prop), bound to that user via `assistantConfig.configurable.externalUserId`.
- **Deliberately does not throw when unauthenticated.** This factory also backs the runtime's `/info` endpoint, which the CopilotKit client SDK probes on every connect to auto-detect transport — and treats *any* non-2xx response as "not REST," silently falling back to a single-route POST protocol this server never registers (`mode: "multi-route"`), which then genuinely 404s with a confusing `agent_connect_failed` error that hides the real cause. So `/info` always succeeds and lists agents regardless of auth state; actual security is enforced downstream, in `OwnedLangGraphAgent.run()`, which hard-rejects any run whose `externalUserId` is missing.
- **CORS**: `createCopilotExpressHandler`'s default is `cors: { origin: "*" }` with no `Access-Control-Allow-Credentials` header — invalid for the frontend's `credentials: "include"` fetches. Browsers reject this outright on any cross-origin-from-the-server's-perspective request (e.g. `127.0.0.1` vs `localhost`, or any real deployment where the API and static assets aren't byte-identical origins), and the CopilotKit client library **silently swallows that rejection** in an empty `catch {}` inside its own auto-detect fallback logic, surfacing as the same confusing 404/`agent_connect_failed` rather than a CORS error — the real cause only shows up as a separate, easy-to-miss "blocked by CORS policy" line in the browser console. `index.ts` passes `cors: { origin: true, credentials: true }` explicitly (`origin: true` reflects the actual request `Origin` instead of a wildcard, which is required once credentials are involved) — don't drop this back to the library default.
- **`OwnedLangGraphAgent`** (subclasses `@ag-ui/langgraph`'s `LangGraphAgent`) does two things on every `run()`:
  1. **Thread-ownership enforcement** (`claimOrVerifyThreadOwnership`, `src/threadOwnership.ts`) — a client-supplied `threadId` must not let one user read/continue another user's conversation; LangGraph's thread store isn't scoped per-caller on its own. First use of a `threadId` claims it for that `externalUserId` (via a unique Mongo index, race-safe); every later use must match, or the run errors with `"This thread belongs to a different user."` **The safety depends entirely on that unique index existing** — `claimOrVerifyThreadOwnership` just does an unconditional `insertOne` and relies on a duplicate-key error to detect an already-claimed thread; if the index is ever missing (e.g. `thread_owners` somehow already has duplicate `threadId`s from before the index existed, so `ensureThreadOwnershipIndexes()`'s `createIndex` fails at every startup with `E11000 duplicate key error`), inserts for that same `threadId` silently succeed instead of raising, both breaking ownership enforcement and crashing server startup outright. Recovery is manual: dedupe `thread_owners` down to one document per `threadId` (keep the earliest), then restart — there's no migration/cleanup script for this in the repo.
  2. **Event sanitization** (`sanitizeEvents`) — strips every `RAW` AG-UI event and every `rawEvent` field from other event types before they reach the browser (see the interaction-model gotcha above for a concrete consequence of this).
  - **Gotcha that bit this once**: `LangGraphAgent.clone()` (called by the CopilotKit runtime per-request/thread) only re-copies fields *it* knows about (`config`, `assistantConfig`, `graphId`, etc.) — it silently drops any extra field a subclass adds in its own constructor. `OwnedLangGraphAgent` originally took `externalUserId` as a constructor param and lost it on every clone (surfaced as a bogus "thread belongs to a different user" — the ownership record showed `externalUserId: null`). Fixed by reading `externalUserId` from `this.assistantConfig.configurable` instead, since `assistantConfig` *is* one of the fields `clone()` explicitly preserves. Don't reintroduce a bespoke instance field on this class without checking it survives `clone()`.
- **Resuming an interrupted run**: the client sends `forwardedProps: { command: { resume: <value> } }` on the next `/agent/<id>/run` call, same `threadId`, empty `messages`. (This is `@langchain/langgraph-sdk`'s run-payload shape, not an AG-UI-standard field — discovered by reading `@ag-ui/langgraph`'s source, not documented anywhere obvious.)

### Manually resuming an interrupt (for debugging without a browser)

`verifyAgUiStream.js` only drives fresh runs, not resumes. To approve/reject/edit a pending plan from the command line: find the thread id (`grep "POST /threads" server/graph.log`, or `POST http://localhost:2024/assistants/search` with `{}` to list assistant ids first), then:

```
curl -X POST http://localhost:2024/threads/<threadId>/runs/stream \
  -H "Content-Type: application/json" \
  -d '{"assistant_id":"<assistant_id for graph_id \"assistant\">","command":{"resume":{"action":"approve"}},"config":{"configurable":{"externalUserId":"<id>"}},"stream_mode":["values"]}'
```

`resume` accepts `{"action":"approve"}`, `{"action":"reject"}`, or `{"action":"update","plan":{...}}` (a full edited `ResearchPlan`). `GET /threads/<threadId>/state` shows the current `plan`/`messages`/pending `interrupts` without resuming anything — useful to confirm what's actually waiting before you decide how to resume it.

### The React app (`web/src/`)

- **`App.tsx`** — session check via `/auth/me`; renders `AuthView` or `ChatView`.
- **`AuthView.tsx`** — login/signup forms calling `/auth/login`, `/auth/signup` (`api.ts`).
- **`ChatView.tsx`** — a single chat, no tabs (there's only one agent now). Wraps `@copilotkit/react-core/v2`'s `<CopilotKit runtimeUrl="/api/copilotkit" credentials="include" useSingleEndpoint={false}>` and `<CopilotChat>`. `useSingleEndpoint={false}` is deliberate, not a default: the client's `"auto"` transport-detection was observed (via server-side request logging — see the CORS note above for the related-but-distinct failure mode) going straight to a broken single-route POST on every attempt in this stack, so forcing `"rest"` explicitly skips relying on that detection rather than debugging why it kept failing. Each user gets one stable `threadId` from `useStableThreadId.ts` (persisted in `localStorage`, keyed by username + the fixed agent id) so a page reload resumes the same LangGraph thread. `<InteractionRenderer />` is mounted alongside `<CopilotChat>` so plan-approval interrupts render inline in the transcript.
- **`InteractionRenderer.tsx`** — the one generic renderer for all three `AgentInteraction` variants (approval buttons, question with recommended options + custom-text fallback, plan editor with add/remove/reorder/skip + Save & Continue) — see the interaction-model gotcha above for its event-shape-normalization logic.
- **`@copilotkit/react-core@1.67.1`'s stable public surface has already moved to an AG-UI-native "v2" API** (`@copilotkit/react-core/v2`, matching `@copilotkit/runtime/v2`/`/v2/express` server-side) — there is no GraphQL runtime anywhere in this integration, despite the package's "1.x" version number suggesting a more mature/settled classic API. Don't reach for `@copilotkit/react-core`'s bare (non-`/v2`) export or any GraphQL-runtime docs/examples you might find online; they don't apply here.

## Keeping prompts/tools in sync

There's only one execution path and one agent now, so there's no cross-file prompt duplication to keep in sync day-to-day. What still needs deliberate care:
- Adding a second specialist agent back (e.g. if `assistant`'s single-model-decides-everything approach turns out to need a hard safety boundary again) means: a new prompt constant, a new `src/graph/*.ts` file (copy `assistantGraph.ts`'s node shape — its plain ReAct loop for a simple agent, or its plan/HITL nodes for one that needs approval), a new entry in `langgraph.json`, a new key in `copilotRuntime.ts`'s `AGENT_GRAPH_IDS`, and either a tab or an explicit routing step back in `web/src/ChatView.tsx` (there's no router left to make that decision server-side, unlike the old removed `router.ts`).
- `assistantGraph.ts`'s `runReactLoop` is currently the only hand-written model-call/tool-execution loop in the codebase — the two others that used to exist alongside it (`simpleAgentGraph.ts`'s unused `buildSimpleAgentGraph` factory, and the unregistered `researchGraph.ts`'s own `runReactLoop`) were deleted in the production cleanup pass since neither had any real caller. If a second graph is added back with its own loop, note that it won't call into this one's logic automatically — a fix to iteration-limit/retry behavior here won't propagate to a new one without deliberately sharing the code.

## Conventions to follow

- The system prompt (`src/assistantPrompt.ts`'s `ASSISTANT_SYSTEM_PROMPT`) is written for the *end user's* voice: plain language, no raw JSON/IDs/GUIDs/tool payloads ever surfaced in a reply, short natural confirmations for simple actions rather than structured reports (research/synthesis answers can be longer and organized). Preserve this tone when editing it, and don't add headers/bullets/bold-label formatting to what's meant to be a short conversational reply. Planning decisions (`plannerNode`) must never expose chain-of-thought — only observable, user-facing step titles/descriptions ever reach the plan the user approves.
- `DEFAULT_TENANT_ID` (`src/constants.ts`, value `"default"`) is threaded through every memory call site. It's an explicit placeholder for future multi-tenancy, not a real feature yet — don't build tenant-switching UI/logic without checking with the user first, and don't remove the parameter thinking it's dead code.
- Structured-output/internal-decision calls should default to `silentJsonCompletion()` (`src/silentModel.ts`) if they run inside a graph node and must never appear as visible chat text — see "Structured decisions that must never appear as chat output" above. Calls that *are* meant to eventually produce visible chat content (the main `model` export) still go through normal LangChain `ChatModel`s.
- Memory writes always go through `MemoryRepository` methods (`src/memory/v2/repository.ts`), never direct `getDb().collection(...)` calls from agent or route code — `collections.ts` is the only file that should call `getDb()` for those collections. (`threadOwnership.ts`'s `threads` collection is a separate concern and reaches `getDb()` directly itself.) `GoalService` writes and advances `GoalRecord`s independently — see "Durable goals" above. New memory collections/routes follow the same rule: `workspaceService.ts`/`memorySettingsService.ts` are the only callers of their respective collections.
- Never trust the client for identity or thread ownership — `copilotRuntime.ts` always re-derives `externalUserId` from the verified session cookie, never from anything in the request body/props, and `OwnedLangGraphAgent` enforces per-thread ownership server-side rather than assuming a `threadId` the client sends is theirs.
